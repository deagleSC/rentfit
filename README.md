# RentFit

Conversational rental search for Indian cities (Bengaluru and Mumbai). Landlords describe a flat in
chat and RentFit builds the listing. Tenants search in plain English or Hinglish, refine with
follow-ups, and get grounded answers whose every number is checked against its source.

| App | URL |
| --- | --- |
| Tenant | https://rentfit-tenant.vercel.app |
| Landlord | https://rentfit-landlord.vercel.app |
| API | https://rentfit-api.vercel.app (`/health`) |

Sign-in is required everywhere; there is no anonymous search.

## What it does

**Landlords** (`apps/landlord`)
- Describe the flat in one message. The listing agent fills a live preview, then asks for whatever
  is still missing. Edits in chat ("bachelors also ok", "make deposit 2 months") go through the same
  code path as the edit form.
- Drop a pin. If it lands in a different area from the one named in chat, the app asks which is right.
- Upload 3-15 photos, which the browser resizes to WebP. Check the rent against comparable listings.
- Publish, pause, resume, mark as let. Reply to tenant enquiries.

**Tenants** (`apps/tenant`)
- Search by chat, e.g. "2 BHK in Koramangala under 40k near metro". Each turn shows filter chips,
  listing cards and map pins, and hovering a card highlights its pin.
- Refine with follow-ups: "thoda sasta" (cheaper), "near metro instead", "what about the 2nd one?".
- When there are fewer than 5 matches, the search loosens one thing at a time and says what it changed.
- Each claim in an answer cites a listing or an OpenStreetMap area note; the chip opens the source.
- Listing detail (photos, nearby places, commute time, area notes), shortlist with comparison, saved
  searches, and enquiries. Contact details are removed from messages.

## Architecture

```
apps/landlord, apps/tenant   Next.js 15 (React 19, Tailwind 4, React Query), Vercel
        │  bearer token (Supabase Auth)
        ▼
apps/api                     FastAPI on Vercel (Python 3.12)
  ├─ agents/                 LangGraph: listing agent, search agent (checkpointed per chat)
  ├─ pipeline/               hybrid search, citations, chunking, redaction, normalisers
  ├─ llm/                    model wrapper: forced tool calls, cache, daily cap, fallback, prompt lock
  └─ jobs/                   Inngest: embed-listing, embed-locality-notes, notify-enquiry, housekeeping
        │
        ▼
Supabase                     Postgres 17 + PostGIS + pgvector + pg_trgm, RLS on every table,
                             Storage (photos), Edge Function `embed` (gte-small)
OpenRouter                   Gemma 4 26B (fallback Gemma 4 31B), 300 calls/day cap
OpenStreetMap                localities, POIs, map tiles (OpenFreeMap)
```

Notable choices are recorded in [`docs/adr/`](docs/adr):
- [one production database, tests in rolled-back transactions](docs/adr/0001-production-only-supabase.md)
- [two model calls per search turn](docs/adr/0003-two-model-calls-per-search-turn.md)
- [claims checked against their citations](docs/adr/0004-citations-checked-in-code.md)
- [relaxing that never rewrites the tenant's filters](docs/adr/0005-relaxing-keeps-the-tenants-filters.md)

The full build plans are in [`docs/plans/`](docs/plans).

How each is measured:
- **Listing extraction** (30 descriptions) and **edits** (20 messages): the agent's own pipeline,
  which is the model plus code backfill and guards. Edits must match the hand edit exactly.
- **Filter parsing** (60 queries, a third of them follow-ups on existing filters): model parse,
  then slang rules, locality lookup and merge.
- **Retrieval** (30 queries over each city's seeded listings, no model): relevance comes from the
  listings' structured data. The seeded descriptions are generated from templates, which favours
  full-text search.
- **Answers** (15 searches): claims the citation checker dropped, over all claims written.
- **Latency**: the deployed API, fresh queries (nothing served from the model cache).

The datasets are smaller than the plan's (60/40/150/100) so a full run fits the 300-call daily cap.

## Running locally

Needs Node 22, pnpm 9, Python 3.12 and uv. Copy `apps/api/.env.example` to `apps/api/.env`,
and each app's `.env.example` to `.env.local`, then fill in the Supabase and OpenRouter values.

```bash
pnpm install
cd apps/api && uv sync && uv run uvicorn app.main:app --reload --port 8000   # API
pnpm --filter @rentfit/landlord dev                                            # :3000
pnpm --filter @rentfit/tenant dev                                              # :3001
```

In dev, `LLM_PROVIDER=fake` makes every prompt answer from deterministic patterns (no network), and
`JOB_DISPATCHER=inline` runs background jobs in-process.

Reference data and seed listings:

```bash
cd apps/api
uv run python -m scripts.seed_reference        # cities, OSM localities and POIs
uv run python -m scripts.build_locality_notes  # OSM area notes + embeddings
uv run python -m scripts.seed                  # 100 template listings (no model calls)
```

## Tests

| What | Command | Where it runs |

| API unit, property, RLS and API tests | `cd apps/api && uv run pytest` | locally (DB tests need `TEST_ADMIN_DATABASE_URL`); CI runs the rest |
| Frontend unit tests | `pnpm turbo run test` | CI |
| Types, lint, OpenAPI drift, bundle budget | `pnpm typecheck && pnpm lint` | CI |

## Deployment

Three Vercel projects (`rentfit-api`, `rentfit-landlord`, `rentfit-tenant`) deploy from `main`.
After each API deploy, CI re-registers the Inngest functions. Database migrations are applied with
`supabase db push`.
